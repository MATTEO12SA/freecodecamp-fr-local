# --description--

Tu as été introduit aux assertions et aux tests unitaires dans une leçon précédente. Pour rappel, les tests unitaires consistent à vérifier la sortie de fonctions ou composants individuels de façon indépendante, par contraste avec le test de la sortie finale de tout le programme. Les assertions servent à vérifier que le code se comporte comme prévu.

Dans cette leçon, on regardera de plus près les assertions dans les tests unitaires et on explorera quelques bonnes pratiques.

Une bibliothèque d'assertions couramment utilisée est Chai. C'est la même bibliothèque utilisée dans le dépôt freeCodeCamp. Chaque fois que tu parcours un workshop ou un lab, une suite de tests automatisés s'exécute contre ton code pour s'assurer qu'il se comporte comme prévu.

Regardons quelques exemples issus du Full-Stack Developer Curriculum.

Dans le workshop Build a Calculator, l'étape 1 teste une fonction appelée `addTwoAndSeven` :

```js
assert.isFunction(addTwoAndSeven);
```

Cette assertion vérifie que le code fourni contient une fonction nommée `addTwoAndSeven`. Si l'utilisateur crée un tableau, une chaîne, ou autre chose qui n'est pas une fonction et l'assigne à `addTwoAndSeven`, alors le test échouera.

Regardons une autre assertion plus loin dans le workshop :

```js
assert.equal(addThreeAndFour(), 7);
```

Cette assertion vérifie que la valeur renvoyée par la fonction `addThreeAndFour` est égale au nombre `7`. Si la valeur renvoyée n'est pas égale à `7`, alors le test échouera.

Il y a bien d'autres asserts intégrés à Chai, comme ceux qui vérifient si une valeur est un booléen, si un objet a un certain nom de propriété, ou si une valeur est `null`. D'autres bibliothèques d'assertions JavaScript courantes sont should.js et expect.js.

Quelle que soit la bibliothèque d'assertions avec laquelle tu travailles, il y a quelques bonnes pratiques à connaître. La première est d'écrire des messages d'assertion clairs. Des messages clairs et significatifs devraient décrire l'intention. Sinon, il sera difficile de localiser quels tests échouent.

Une autre bonne pratique est d'écrire des messages d'échec descriptifs. Un message d'échec descriptif devrait indiquer quelle condition est vraie. Cela t'aidera à comprendre pourquoi une assertion particulière échoue.

En continuant à apprendre à coder, il est important de te familiariser avec les tests et de commencer à écrire des tests pour tes projets personnels. Cela t'aidera beaucoup à te préparer pour ton premier poste de développeur.
