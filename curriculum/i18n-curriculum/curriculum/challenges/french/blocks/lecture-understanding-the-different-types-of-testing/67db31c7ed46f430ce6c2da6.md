# --description--

Le mocking consiste à remplacer de vraies données par de fausses données qui simulent le comportement de vrais composants. Cela permet aux testeurs et développeurs de tester des composants spécifiques de l'application sans dépendre de dépendances externes.

Un cas d'usage courant pour mocker des données serait quand on traite des appels API. Imagine que tu as un appel fetch comme ceci dans ton application :

```js
export const postService = {
  async getPosts() {
    const response = await fetch("https://api.example.com/posts");
    return response.json();
  },
};
```

Si tu dois tester la fonction `postService`, tu pourrais mocker la réponse de l'API au lieu de faire des appels API continus pour récupérer les données. Récupérer depuis une API prend du temps et dépend de facteurs externes comme la disponibilité du réseau et les réponses serveur. Moquer la réponse de l'API retire ces facteurs externes et permet aux testeurs de travailler avec un jeu de données prévisible et contrôlé.

Voici un exemple de réponse API mockée :

```json
[
  {
    "id": 1,
    "title": "Understanding Async/Await in JavaScript",
    "content": "Async/Await makes asynchronous code look and behave like synchronous code...",
    "author": "Jane Doe",
    "created_at": "2025-04-10T14:32:00Z"
  },
  {
    "id": 2,
    "title": "10 Tips for Writing Clean Code",
    "content": "Clean code is not just about code formatting. It involves naming, architecture...",
    "author": "John Smith",
    "created_at": "2025-04-08T09:21:00Z"
  },
  {
    "id": 3,
    "title": "Exploring React 19 Features",
    "content": "React 19 comes with exciting features like new hooks and better performance...",
    "author": "Alex Lee",
    "created_at": "2025-04-07T18:47:00Z"
  }
]
```

Maintenant qu'on comprend ce qu'est le mocking, comparons-le au stubbing. Les stubs sont des objets qui renvoient des réponses prédéfinies ou des données factices pour un comportement attendu dans une application. Par exemple, tu peux stubber le comportement d'une connexion à une base de données dans tes tests sans dépendre d'une vraie connexion.

Voici un exemple de stub dans Jest :

```js
import { postService } from "./postService";
import { db } from "./db";

jest.mock("./db", () => ({
  db: {
    fetchPosts: jest.fn(),
  },
}));

test("should return stubbed posts", async () => {
  const fakePosts = [
    { id: 1, title: "Stubbed Post", content: "This is a stubbed post." },
  ];

  db.fetchPosts.mockResolvedValue(fakePosts);

  const posts = await postService.getPosts();

  expect(posts).toEqual(fakePosts);
});
```

`db.fetchPosts.mockResolvedValue(fakePosts);` est le stub dans cet exemple.

Le dernier composant à discuter, ce sont les fakes. Les fakes sont des versions simplifiées de vrais composants, sans la complexité ni les effets de bord du vrai. Par exemple, tu peux faker une base de données en stockant les données en mémoire au lieu d'interagir avec la vraie base. Cela te permet de mimer les opérations de base de données en mémoire, bien plus vite qu'avec la vraie base. Un autre exemple courant serait d'utiliser des fakes avec les systèmes de fichiers. Tu peux créer un faux système de fichiers à la place du vrai pour les tests.

En continuant à construire des applications logicielles plus complexes, envisage d'utiliser des mocks, stubs ou fakes là où c'est approprié dans tes tests.
