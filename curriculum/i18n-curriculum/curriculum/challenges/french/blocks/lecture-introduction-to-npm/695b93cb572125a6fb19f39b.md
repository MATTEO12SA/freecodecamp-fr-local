# --description--

Le versionnage sémantique, ou SemVer, est un système qui donne un sens clair aux numéros de version, pour que les développeurs puissent rapidement comprendre quel type de changements a été apporté au logiciel.

SemVer utilise ce format :

```bash
MAJOR.MINOR.PATCH
```

Par exemple, la bibliothèque populaire `lodash` est actuellement en version `4.17.21`.

Voici ce que signifie chaque partie :

* MAJOR — Grands changements qui cassent le code existant. Exemple : supprimer ou renommer une fonction dont le code existant pourrait dépendre.

* MINOR — Nouvelles fonctionnalités qui ne cassent pas le code existant. Exemple : ajouter une nouvelle fonction ou un paramètre optionnel.

* PATCH — Petites corrections et améliorations. Exemple : corriger un bug ou une faute de frappe sans changer le fonctionnement.

<img src="https://cdn.freecodecamp.org/curriculum/lecture-transcripts/what-is-semantic-versioning-1.png" alt="Dans le numéro de version 4.17.21, 4 est la version majeure, changée pour les breaking changes, 17 est la version mineure, changée pour les changements non cassants, et 21 est le patch, changé pour les corrections de bugs et petites fonctionnalités">

Disons que tu as un paquet appelé `my-package`. Voici un exemple de la façon dont son numéro de version pourrait évoluer avec le versionnage sémantique :

| Version | Ce qui a changé |
| --- | --- |
| 1.0.0 | Première version stable |
| 1.1.0 | Nouvelle fonctionnalité optionnelle |
| 1.1.1 | Petite correction de bug ou fonctionnalité |
| 2.0.0 | Breaking changes introduits |

Mais il y a plus à savoir sur les numéros de version dans npm. Quand tu installes un paquet, la version dans ton fichier `package.json` peut ressembler à ceci :

```json
"lodash": "^4.17.21"
```

Tu as déjà appris que `4` est la version majeure, `17` la version mineure, et `21` la version de patch. Mais que signifie le caret (`^`) devant ?

Le symbole caret permet à npm d'installer automatiquement des versions mineures et de patch plus récentes (`4.x.x`), mais pas de nouvelles versions majeures (`5.x.x`), car les mises à jour majeures peuvent inclure des breaking changes.

Quand la version majeure est `0`, le caret devient plus restrictif. Par exemple, `^0.2.3` autoriserait des mises à jour comme `0.2.4`, mais pas `0.3.0`, car les versions majeures commençant par `0` sont considérées comme moins stables.

Le caret n'est pas le seul symbole que `npm` et d'autres gestionnaires de paquets JavaScript utilisent pour gérer les versions des dépendances.

Il y a le symbole tilde (`~`) qui n'autorise que les mises à jour de la version de patch. Donc, `~1.2.3` accepterait `1.2.4` et `1.2.9`, mais jamais `1.3.0`.

Tu peux aussi utiliser le plus grand que (`>`), le plus petit que (`<`), et leurs équivalents « ou égal » pour accepter des versions dans une plage. Par exemple, `>=1.2.3 <2.0.0` signifie toute version de `1.2.3` jusqu'à, mais sans inclure, `2.0.0`.

Le symbole astérisque (`*`) correspond à n'importe quelle version, donc il accepte tout. C'est idéal uniquement pour les tests et non recommandé en production.

Enfin, tu peux verrouiller une version exacte en ne préfixant le numéro de version d'aucun symbole. Par exemple, la version `1.2.3` n'accepte que `1.2.3`.

Voici un tableau récapitulatif rapide :

| Symbole | Signification | Plage d'exemple |
| --- | --- | --- |
| `^` | Autoriser mises à jour mineures + patch | `^1.2.3` → `1.x.x` |
| `~` | Autoriser mises à jour de patch uniquement | `~1.2.3` → `1.2.x` |
| `>`, `<`, `>=`, `<=` | Plage personnalisée | `>=1.2.3` ou `<2.0.0` |
| **\*** | Toute version | toutes les versions |
| aucun | Version exacte | `1.2.3` |
