## Tests manuels et automatisés

- **Tests manuels** : En tests manuels, un testeur parcourt manuellement chaque partie de l'application et teste différentes fonctionnalités pour s'assurer qu'elles fonctionnent correctement. Si des bugs sont découverts, le testeur les signale à l'équipe logicielle pour qu'ils soient corrigés.
- **Tests automatisés** : En tests automatisés, tu peux automatiser tes tests en écrivant un programme séparé qui vérifie si ton application se comporte comme prévu.

## Tests unitaires

- **Tests unitaires** : En tests unitaires, tu testes chaque fonction pour t'assurer que tout fonctionne comme prévu. Les tests unitaires peuvent aussi servir de documentation pour ton application, car ils sont censés représenter le comportement attendu de ton code.
- **Principe de responsabilité unique** : Le principe de responsabilité unique recommande de garder chaque fonction petite et responsable d'une seule chose.
- **Frameworks de test JavaScript courants** : Parmi les frameworks courants, on trouve Jest, Mocha et Vitest. Jest est un framework populaire pour les tests unitaires.

Voici un exemple de tests unitaires avec Jest.

D'abord, tu peux créer une fonction responsable de renvoyer une chaîne nouvellement formatée :

```javascript
export function getFormattedWord(str) {
  if (!str) return '';
  return str.charAt(0).toUpperCase() + str.slice(1);
}
```

Dans un fichier séparé `getFormattedWord.test.js`, tu peux écrire des tests pour vérifier que la fonction fonctionne comme prévu. Le fichier `getFormattedWord.test.js` ressemblera à ceci :

```javascript
import { getFormattedWord } from "./getFormattedWord.js";
import { test, expect } from "jest";

test('capitalizes the first letter of a word', () => {
  expect(getFormattedWord('hello')).toBe('Hello');
});
```

- **Fonction `expect`** : La fonction `expect` sert à tester une valeur.
- **Matcher** : Un matcher est une fonction qui vérifie si la valeur se comporte comme prévu. Dans l'exemple ci-dessus, le matcher est `toBe()`. Jest propose une variété de matchers.

Pour utiliser Jest, tu dois d'abord installer le paquet `jest` avec `npm i jest`. Tu devras aussi ajouter un script à ton fichier `package.json` comme ceci :

```js
"scripts": {
  "test": "jest"
},
```

Ensuite, tu peux lancer la commande `npm run test` pour exécuter tes tests.

## Cycle de vie du développement logiciel

- **Différentes étapes du cycle de vie du développement logiciel** :
  - **Étape de planification** : L'équipe de développement recueille les exigences du travail proposé auprès des parties prenantes.
  - **Étape de conception** : L'équipe logicielle décompose les exigences et décide des meilleures approches pour les solutions.
  - **Étape d'implémentation** : L'équipe logicielle découpe les exigences en tâches gérables et les implémente.
  - **Étape de tests** : Cela implique des tests manuels et automatisés pour le nouveau travail. Parfois, l'équipe teste l'application tout au long du développement pour attraper et corriger les problèmes qui apparaissent.
  - **Étape de déploiement** : L'équipe déploie les nouveaux changements dans un environnement de build ou de test.
  - **Étape de maintenance** : Cela implique de corriger les problèmes signalés par les clients dans l'application en production.

- **Différents modèles du cycle de vie du développement logiciel** :
  - **Modèle en cascade (Waterfall)** : Dans le modèle Waterfall, chaque phase du cycle doit être terminée avant que la suivante puisse commencer.
  - **Modèle Agile** : Le modèle Agile se concentre sur le développement itératif en découpant le travail en sprints.

## BDD et TDD

- **TDD** : Le développement piloté par les tests (Test-driven development) est une méthodologie qui met l'accent sur l'écriture des tests en premier. Écrire les tests avant de construire les fonctionnalités donne un retour en temps réel aux développeurs pendant le développement.
- **BDD** : Le développement piloté par le comportement (Behavior-driven development) consiste à aligner une série de tests sur les objectifs métier. Les scénarios de test en BDD doivent être écrits dans un langage compréhensible par les personnes techniques et non techniques. Un exemple de telle syntaxe est Gherkin.
- **Frameworks de test BDD** : Des exemples de frameworks BDD incluent Cucumber, JBehave et SpecFlow.

## Assertions dans les tests unitaires

- **Assertion** : Les assertions servent à vérifier que le code se comporte comme prévu.
- **Bibliothèques d'assertions** : Chai est une bibliothèque d'assertions couramment utilisée. D'autres bibliothèques JavaScript courantes sont `should.js` et `expect.js`.

Voici un exemple d'assertion avec Chai qui vérifie que la valeur renvoyée par la fonction `addThreeAndFour` est égale au nombre 7 :

```js
assert.equal(addThreeAndFour(), 7);
```

- **Bonnes pratiques** : Quelle que soit la bibliothèque d'assertions que tu utilises, tu devrais écrire des messages d'assertion et d'échec clairs qui t'aideront à comprendre quels tests échouent et pourquoi.

## Mocking, faking et stubbing

- **Mocking** : Le mocking consiste à remplacer de vraies données par de fausses données qui simulent le comportement de vrais composants. Par exemple, tu pourrais mocker la réponse d'une API en test au lieu de faire des appels API continus pour récupérer les données.
- **Stubbing** : Les stubs sont des objets qui renvoient des réponses prédéfinies ou des données factices pour un comportement attendu dans une application. Par exemple, tu peux stubber le comportement d'une connexion à une base de données dans tes tests sans dépendre d'une vraie connexion.
- **Faking** : Les fakes sont des versions simplifiées de vrais composants, sans la complexité ni les effets de bord. Par exemple, tu peux faker une base de données en stockant les données en mémoire au lieu d'interagir avec la vraie base. Cela te permet de mimer les opérations de base de données en mémoire, bien plus vite qu'avec la vraie base.

## Tests fonctionnels

- **Tests fonctionnels** : Les tests fonctionnels vérifient si les fonctionnalités de l'application marchent comme prévu. L'objectif est de tester le système dans son ensemble face à plusieurs scénarios.
- **Tests non fonctionnels** : Les tests non fonctionnels se concentrent sur des aspects comme la performance et la fiabilité.
- **Smoke testing** : Le smoke testing est une vérification préliminaire du système pour détecter des problèmes basiques ou critiques avant de commencer des tests plus poussés.

## Tests de bout en bout

- **Tests de bout en bout** : Les tests de bout en bout, ou E2E, testent des scénarios réels du point de vue de l'utilisateur. Ils aident à s'assurer que ton application se comporte correctement et de façon prévisible pour les utilisateurs. Cependant, ils sont longs à mettre en place, concevoir et maintenir.
- **Frameworks de tests de bout en bout** : Playwright est un framework E2E populaire développé par Microsoft. D'autres outils E2E incluent Cypress, Selenium et Puppeteer.

Voici un exemple de tests E2E issus du dépôt freeCodeCamp avec Playwright. Le hook `beforeEach` s'exécute avant chacun des tests. Les tests vérifient que le donateur a un lien supporter dans la barre de menu, ainsi qu'une bordure stylisée spéciale autour de son avatar :

```js
test.beforeEach(async ({ page }) => {
  execSync("node ./tools/scripts/seed/seed-demo-user --set-true isDonating");
  await page.goto("/donate");
});

...

test("The menu should have a supporters link", async ({ page }) => {
  const menuButton = page.getByTestId("header-menu-button");
  const menu = page.getByTestId("header-menu");

  await expect(menuButton).toBeVisible();
  await menuButton.click();

  await expect(menu).toBeVisible();

  await expect(page.getByRole("link", { name: "Supporters" })).toBeVisible();
});

test("The Avatar should have a special border for donors", async ({ page }) => {
  const container = page.locator(".avatar-container");
  await expect(container).toHaveClass("avatar-container gold-border");
});
```

## Tests d'utilisabilité

- **Tests d'utilisabilité** : Les tests d'utilisabilité consistent à faire interagir de vrais utilisateurs avec l'application pour découvrir s'il y a des problèmes de design, d'expérience utilisateur ou de fonctionnalités. Ils se concentrent sur le caractère intuitif de l'application pour les utilisateurs.
- **Quatre types courants de tests d'utilisabilité** :
  - **Exploratoire** : Les tests d'utilisabilité exploratoires impliquent que les utilisateurs interagissent avec les différentes fonctionnalités pour mieux comprendre comment elles marchent.
  - **Comparatif** : Les tests comparatifs comparent l'expérience utilisateur de ton application avec des applications similaires sur le marché.
  - **Évaluation** : Les tests d'évaluation étudient à quel point l'application est intuitive à utiliser.
  - **Validation** : Les tests de validation identifient les problèmes majeurs qui empêcheraient l'utilisateur d'utiliser l'application efficacement.
- **Outils de tests d'utilisabilité** : Des exemples d'outils incluent Loop11, Maze, Userbrain, UserTesting et UXTweak.

## Tests de compatibilité

- **Tests de compatibilité** : L'objectif des tests de compatibilité est de s'assurer que ton application fonctionne dans différents environnements informatiques.
- **Différents types de tests de compatibilité** :
  - **Compatibilité ascendante (backwards)** : La compatibilité ascendante signifie que le logiciel est compatible avec les versions antérieures.
  - **Compatibilité descendante (forwards)** : La compatibilité descendante signifie que le logiciel et les systèmes fonctionneront avec les versions futures.
  - **Compatibilité matérielle** : C'est la capacité du logiciel à fonctionner correctement dans différentes configurations matérielles.
  - **Compatibilité des systèmes d'exploitation** : C'est la capacité du logiciel à fonctionner sur différents OS, comme macOS, Windows, et des distributions Linux comme Ubuntu et Fedora.
  - **Compatibilité réseau** : Cela signifie que le logiciel peut fonctionner dans différentes conditions réseau : vitesses, protocoles, paramètres de sécurité, etc.
  - **Compatibilité navigateurs** : Cela signifie que l'application web fonctionne de façon cohérente sur différents navigateurs, comme Google Chrome, Safari, Firefox, etc.
  - **Compatibilité mobile** : Il est important de s'assurer que tes applications fonctionnent sur une variété d'appareils Android et iOS, y compris téléphones et tablettes.

## Tests de performance

- **Tests de performance** : En tests de performance, tu évalues la vitesse, la réactivité, la scalabilité et la stabilité d'une application sous différentes charges. L'objectif est de résoudre tout goulot d'étranglement de performance.
- **Différents types de tests de performance** :
  - **Load testing** : Le load testing détermine comment un système se comporte en charge normale et en pic.
  - **Stress testing** : Le stress testing consiste à tester ton application sous des charges extrêmes et à voir comment le système répond.
  - **Soak testing (endurance)** : Le soak testing ou test d'endurance est un type de load testing où tu testes le système avec une charge élevée pendant une période prolongée.
  - **Spike testing** : Le spike testing consiste à augmenter et diminuer dramatiquement les charges et à analyser les réactions du système.
  - **Breakpoint testing (capacity)** : Le breakpoint testing ou capacity testing consiste à augmenter lentement la charge jusqu'au point où le système commence à échouer ou à se dégrader.

## Tests de sécurité

- **Tests de sécurité** : Les tests de sécurité aident à identifier les vulnérabilités et les faiblesses.
- **Principes de sécurité** :
  - **Confidentialité** : Cela protège contre la divulgation d'informations sensibles à des destinataires non prévus.
  - **Intégrité** : Cela implique d'empêcher des utilisateurs malveillants de modifier les informations utilisateur.
  - **Authentification** : Cela implique de vérifier l'identité de l'utilisateur pour s'assurer qu'il est autorisé à utiliser le système.
  - **Autorisation** : C'est le processus qui détermine quelles actions les utilisateurs authentifiés peuvent effectuer, ou quelles parties du système ils peuvent accéder.
  - **Disponibilité** : Cela garantit que les informations et services sont disponibles pour les utilisateurs autorisés quand ils en ont besoin.
  - **Non-répudiation** : Cela garantit que l'émetteur et le destinataire ont une preuve de livraison et une vérification de l'identité de l'émetteur. Cela protège contre le déni d'avoir envoyé l'information.
- **Menaces de sécurité courantes** :
  - **Cross-Site Scripting (XSS)** : Les attaques XSS surviennent quand un attaquant injecte des scripts malveillants dans une page web, puis les exécute dans le contexte du navigateur de la victime.
  - **Injection SQL** : L'injection SQL permet à des utilisateurs malveillants d'injecter du code malveillant dans une base de données.
  - **Attaque par déni de service (DoS)** : Une attaque DoS survient quand des utilisateurs malveillants inondent un site d'un grand nombre de requêtes ou de trafic, ce qui ralentit le serveur et peut le faire planter, rendant le site indisponible.
- **Catégories d'outils de tests de sécurité** :
  - **Static Application Security Testing** : Ces outils évaluent le code source d'une application pour identifier des vulnérabilités de sécurité.
  - **Dynamic Application Security Testing** : Ces outils s'interfacent avec le front-end de l'application pour découvrir des faiblesses de sécurité potentielles. Les outils DAST n'ont pas accès au code source.
- **Tests de pénétration (pentest)** : Les tests de pénétration sont un type de tests de sécurité qui consiste à créer des cyberattaques simulées sur l'application pour identifier des vulnérabilités dans le système.

## Tests A/B

- **Tests A/B** : Les tests A/B comparent deux versions d'une page ou d'une application et étudient laquelle performe mieux. On les appelle aussi bucket testing ou split testing. Ils te permettent de prendre des décisions plus fondées sur les données et d'améliorer continuellement l'expérience utilisateur.
- **Outils pour les tests A/B** : Des exemples d'outils incluent GrowthBook et LaunchDarkly.

## Tests alpha et bêta

Une fois le développement initial et les tests logiciels terminés, il est important de faire tester l'application par des testeurs et de vrais utilisateurs. C'est là qu'interviennent les tests alpha et bêta.

- **Tests alpha** : Les tests alpha sont réalisés par un groupe sélectionné de testeurs qui parcourent l'application pour s'assurer qu'il n'y a pas de bugs avant sa sortie sur le marché. Les tests alpha font partie des tests d'acceptation et utilisent des techniques de tests en boîte blanche et en boîte noire.
- **Tests bêta** : Les tests bêta consistent à rendre l'application disponible à de vrais utilisateurs. Les utilisateurs peuvent interagir avec l'application et fournir des retours. Les tests bêta sont aussi une forme de tests d'acceptation utilisateur.
- **Tests d'acceptation** : Les tests d'acceptation s'assurent que l'application logicielle répond aux exigences métier et aux besoins des utilisateurs avant sa sortie.
- **Tests en boîte noire** : Les tests en boîte noire se concentrent uniquement sur le comportement attendu de l'application.
- **Tests en boîte blanche** : Les tests en boîte blanche impliquent que le testeur connaisse les composants internes et effectue des tests dessus.

## Tests de régression

- **Régression** : Une régression désigne les situations où de nouveaux changements cassent involontairement des fonctionnalités existantes.
- **Tests de régression** : Les tests de régression aident à attraper les problèmes de régression. Tu réexécutes des tests fonctionnels sur des parties de ton application pour t'assurer que tout fonctionne encore comme prévu.
- **Outils pour les tests de régression** : Parmi les outils utilisables : Puppeteer, Playwright, Selenium et Cypress.
- **Techniques de tests de régression** :
  - **Tests de régression unitaires** : Tu as une liste d'éléments à tester chaque fois que des changements majeurs ou des correctifs sont implémentés dans l'app.
  - **Tests de régression partiels** : Approches ciblées pour s'assurer que les nouveaux changements n'ont pas cassé des aspects spécifiques de l'application.
  - **Tests de régression complets** : On exécute des tests sur toutes les fonctionnalités du codebase. C'est l'option la plus longue et la plus détaillée.
- **Retesting** : Le retesting sert à vérifier des problèmes connus et à s'assurer qu'ils ont été résolus. En contraste, les tests de régression cherchent des problèmes inconnus qui auraient pu apparaître suite à des changements récents dans le codebase.
