## Bibliothèques et frameworks JavaScript

- Les bibliothèques et frameworks JavaScript offrent des solutions rapides aux problèmes courants et accélèrent le développement en fournissant du code préécrit.
- Les bibliothèques se concentrent généralement sur des tâches précises, comme manipuler le DOM, gérer les événements ou les requêtes AJAX.
- Quelques exemples de bibliothèques JavaScript sont jQuery et React.
- Les frameworks, eux, fournissent une structure plus définie pour construire des applications. Ils s’accompagnent souvent de règles et de conventions que les développeurs doivent suivre.
- Des exemples de frameworks incluent Angular et Next.js, un méta-framework pour React.
- Les **applications monopage** (SPA) sont des applications web qui chargent une seule page HTML et mettent à jour cette page dynamiquement quand l’utilisateur interagit, sans recharger toute la page.
- Les SPA utilisent JavaScript pour gérer le state de l’application et rendre le contenu. On le fait souvent avec des frameworks qui offrent d’excellents outils pour construire des interfaces utilisateur complexes.
- Quelques problèmes liés aux SPA :

  - Les lecteurs d’écran peinent avec le contenu mis à jour dynamiquement.
  - L’URL ne change pas quand l’utilisateur navigue dans l’application, ce qui peut rendre difficile de mettre en favori, revenir en arrière ou partager des pages précises.
  - Le temps de chargement initial peut être lent si l’application est volumineuse, car tous les assets doivent être chargés d’emblée.

## React

- React est une bibliothèque JavaScript populaire pour construire des interfaces utilisateur et des applications web.
- Un concept central de React est la création de composants d’UI réutilisables qui peuvent se mettre à jour et se rendre indépendamment quand les données changent.
- React permet aux développeurs de décrire à quoi l’UI doit ressembler en fonction du state de l’application. React met ensuite à jour et rend les bons composants quand les données ou le state changent.

## Composants React

- Les composants sont les briques de base des applications React : ils permettent de découper des interfaces complexes en morceaux plus petits et gérables.
- L’UI est décrite avec JSX, une extension de la syntaxe JavaScript qui permet d’écrire du code proche du HTML dans JavaScript.
- Les composants sont essentiellement des fonctions ou des classes JS qui renvoient un morceau d’UI.

Voici un exemple de composant React simple qui affiche un message de salutation :

```jsx
function Greeting() {
  const name = 'Anna';
  return <h1>Welcome, {name}!</h1>;
}
```

Pour utiliser le composant, tu peux simplement appeler :
```jsx
  <Greeting />
```

## Importer et exporter des composants React

- Un export rend un composant disponible pour d’autres fichiers. Un import permet à un fichier d’utiliser un composant exporté ailleurs.
- Il existe deux types d’exports dans React : les exports par défaut et les exports nommés.

**Exports par défaut**

- Un fichier ne peut avoir qu’un seul export par défaut. C’est idéal pour un fichier qui contient surtout un seul composant.
- Tu peux exporter un composant en export par défaut comme ceci :

```jsx
// City.js
function City() {
  return <p>New York</p>;
}

export default City;
```

- Tu peux aussi exporter sur la même ligne que la définition du composant :

```jsx
export default function City() {
  return <p>New York</p>;
}
```

- Pour importer un export par défaut, utilise le mot-clé `import` sans accolades :

```jsx
// App.js
import City from './City';

function App() {
  return (
    <div>
      <h1>My favorite city is:</h1>
      <City />
    </div>
  );
}
```

**Exports nommés**

- Les exports nommés permettent à un fichier de partager plusieurs composants. Contrairement aux exports par défaut, ils doivent être importés avec le nom exact sous lequel ils ont été exportés.
- Tu peux exporter plusieurs composants depuis le même fichier comme ceci :

```jsx
// Animals.jsx
export function Cat() {
  return <h2>Mr. Whiskers</h2>;
}

export function Dog() {
  return <h2>Fido</h2>;
}
```

- Pour importer des exports nommés, utilise des accolades avec les noms exacts exportés :

```jsx
import { Cat, Dog } from './Animals';
```

- Tu peux renommer un export nommé à l’import avec le mot-clé `as` :

```jsx
import { Cat as Kitty } from './Animals';
```

**Exports mixtes (par défaut et nommés)**

- Un fichier peut avoir un export par défaut et plusieurs exports nommés en même temps :

```jsx
// Animals.jsx
export default function Cat() {
  return <h2>Mr. Whiskers</h2>;
}

export function Dog() {
  return <h2>Fido</h2>;
}
```

- Quand tu importes des exports mixtes, l’export par défaut vient en premier (sans accolades), suivi des exports nommés (entre accolades) :

```jsx
import Cat, { Dog } from './Animals';
```

## Configurer un projet React avec Vite

- Les outils de démarrage de projet et les CLI offrent un moyen rapide et simple de lancer de nouveaux projets, pour que les développeurs se concentrent sur le code plutôt que sur la configuration.
- Vite est un outil de setup populaire et peut être utilisé avec React.
- Pour créer un nouveau projet avec Vite, tu peux utiliser la commande suivante dans ton terminal :

```bash
npm create vite@latest my-react-app -- --template react
```

Cette commande crée un nouveau projet React nommé `my-react-app` avec le template React de Vite. Dans le répertoire du projet, tu verras un fichier `package.json` avec les dépendances et les commandes du projet.

- Pour lancer le projet, va dans le répertoire du projet et exécute les commandes suivantes :

```bash
cd my-react-app # path to the project directory
npm install # installs the dependencies listed in the package.json file
```

- Une fois les dépendances installées, tu devrais voir un nouveau dossier dans ton projet appelé `node_modules`.

- Le dossier `node_modules` est l’endroit où sont stockés tous les packages et bibliothèques requis par ton projet.

- Pour lancer ton projet, utilise la commande suivante :

```bash
npm run dev
```

- Ensuite, ouvre ton navigateur et va sur `http://localhost:5173` pour voir ton application React en cours d’exécution.

- Pour voir le code du template de démarrage, tu peux aller dans le dossier `src` de ton projet et tu devrais voir le fichier `App.jsx`.

## Passer des props dans les composants React

- Dans React, les props (abréviation de properties) permettent de passer des données d’un composant parent à un composant enfant. Ce mécanisme est nécessaire pour créer des éléments d’UI réutilisables et dynamiques.
- Les props peuvent être n’importe quelle valeur JavaScript. Pour passer des props d’un parent à un enfant, tu les ajoutes comme attributs quand tu utilises le composant enfant dans le JSX du parent. Voici un exemple simple :

```jsx
// Parent component
function Parent() {
  const name = 'Anna';
  return <Child name={name} />;
}

// Child component
function Child(props) {
  return <h1>Hello, {props.name}!</h1>;
}
```

Tu peux passer plusieurs props avec l’opérateur spread `(...)`, après les avoir converties en objet. Voici un exemple :
```jsx
// Parent component
function Parent() {
  const person = {
    name: 'Anna',
    age: 25,
    city: 'New York'
  };
  return <Child {...person} />;
}
```

Dans ce code, l’opérateur spread `{...person}` convertit l’objet person en props individuelles passées au composant Child.

## Rendu conditionnel dans React

- Le rendu conditionnel dans React te permet de créer des interfaces dynamiques. Il sert à afficher un contenu différent selon certaines conditions ou états dans ton application.
- Il existe plusieurs façons de rendre du contenu conditionnellement dans React. Une approche courante est d’utiliser l’opérateur ternaire. Voici un exemple :

```jsx
function Greeting({ isLoggedIn }) {
  return (
    <div>
      {isLoggedIn ? <h1>Welcome back!</h1> : <h1>Please log in</h1>}
    </div>
  );
}
```

- Une autre façon de rendre du contenu conditionnellement est d’utiliser l’opérateur logique ET (`&&`). C’est utile quand tu veux afficher du contenu seulement si une certaine condition est remplie. Voici un exemple :

```jsx
function Greeting({ user }) {
  return (
    <div>
      {user && <h1>Welcome, {user.name}!</h1>}
    </div>
  );
}
```

Dans le code ci-dessus, l’élément `h1` n’est rendu que si l’objet user est truthy.

Tu peux aussi utiliser une instruction `if` directe de cette façon :

```js
function Greeting({ isLoggedIn }) {
  if (isLoggedIn) {
    return <h1>Welcome back!</h1>;
  }
  return <h1>Please sign in</h1>;
}
```

## Afficher des listes dans React

- Afficher des listes dans React est une tâche courante quand on construit des interfaces.
- Les listes peuvent être rendues avec la méthode `map()` des tableaux JS pour parcourir un tableau d’éléments et renvoyer un nouveau tableau d’éléments JSX.
- Par exemple, si tu as un tableau de noms que tu veux afficher en liste, tu peux faire ceci :

```jsx
function NameList({ names }) {
  return (
    <ul>
      {names.map((name, index) => (
        <li key={`${name}-${index}`}>{name}</li>
      ))}
    </ul>
  );
}
```

- Pense toujours à fournir une clé unique pour chaque élément de liste afin d’aider React à gérer la mise à jour et le rendu. Avec ces techniques, tu peux créer des listes flexibles, efficaces et dynamiques dans tes applications React.

## Styles en ligne dans React

- Les styles en ligne dans React te permettent d’appliquer des styles CSS directement aux éléments JSX via des objets JavaScript.
- Pour appliquer des styles en ligne dans React, tu peux utiliser l’attribut style sur les éléments JSX. L’attribut style prend un objet dont les clés sont des propriétés CSS en camelCase et les valeurs les valeurs correspondantes. Voici un exemple :

```js
function Greeting() {
  return (
    <h1
      style={{ color: 'blue', fontSize: '24px', backgroundColor: 'lightgray' }}
    >
      Hello, world!
    </h1>
  );
}

export default Greeting;
```

Tu peux aussi extraire les styles dans un objet séparé et le référencer dans l’attribut `style` de cette façon :

```jsx
function Greeting() {

  const styles = {
    color: 'blue',
    fontSize: '24px',
    backgroundColor: 'lightgray'
  };

  return <h1 style={styles}>Hello, world!</h1>;
}

export default Greeting;
```

- Les styles en ligne prennent en charge le style dynamique en te permettant d’appliquer conditionnellement des styles selon les props ou le state. Voici un exemple d’application conditionnelle de styles selon une prop :

```jsx
function Greeting({ isImportant }) {

  const styles = {
    color: isImportant ? 'red' : 'black',
    fontSize: isImportant ? '24px' : '16px'
  };

  return <h1 style={styles}>Hello, world!</h1>;
}

export default Greeting;
```

- Dans le code ci-dessus, les styles `color` et `fontSize` sont définis conditionnellement selon la prop `isImportant`.

## Travailler avec les événements dans React

- **Système d’événements synthétiques** : c’est la façon dont React gère les événements. Il sert de wrapper autour des événements natifs comme `click`, `keydown` et `submit`. Les gestionnaires d’événements dans React utilisent la convention camelCase. (Ex. `onClick`, `onSubmit`, etc.)

Voici un exemple d’utilisation de l’attribut `onClick` pour un élément `button` dans React :

```jsx
function handleClick() {
  console.log("Button clicked!");
}

<button onClick={handleClick}>Click Me</button>;
```

Dans React, les fonctions gestionnaires d’événements commencent souvent par le préfixe `handle` pour indiquer qu’elles gèrent des événements, comme `handleClick` ou `handleSubmit`.

Quand une action utilisateur déclenche un événement, React passe un objet Synthetic Event à ton gestionnaire. Cet objet se comporte beaucoup comme l’objet Event natif en JavaScript vanilla, avec des propriétés comme `type`, `target` et `currentTarget`.

Pour empêcher des comportements par défaut comme le rechargement du navigateur pendant un événement `onSubmit`, par exemple, tu peux appeler la méthode `preventDefault()` :

```jsx
function handleSubmit(event) {
  event.preventDefault();
  console.log("Form submitted!");
}

<form onSubmit={handleSubmit}>
  <input type="text" />
  <button>Submit</button>
</form>;
```

Tu peux aussi envelopper une fonction gestionnaire dans une fonction fléchée comme ceci :

```jsx
function handleDelete(id) {
  console.log("Deleting item:", id);
}

<button onClick={() => handleDelete(1)}>Delete Item</button>;
```

## Travailler avec le state et le hook `useState`

- **Définition du state** : dans React, le state est un objet qui contient des données pour un composant. Quand le state se met à jour, le composant se re-rend. React traite le state comme immuable : tu ne dois pas le modifier directement.
- **Hook `useState()`** : le hook `useState` est une fonction qui te permet de déclarer des variables d’état dans des composants fonctionnels. Voici une syntaxe de base :

```js
const [stateVariable, setStateFunction] = useState(initialValue);
```

Dans la variable d’état, tu as ce qui suit :

- `stateVariable` contient la valeur actuelle du state
- `setStateFunction` (la fonction setter) met à jour la variable d’état
- `initialValue` définit le state initial

Voici un exemple complet pour un composant `Counter` :

```jsx
import { useState } from "react";

function Counter() {
  const [count, setCount] = useState(0);

  return (
    <div>
      <h2>{count}</h2>

      <button onClick={() => setCount(count - 1)}>Decrement</button>
      <button onClick={() => setCount(count + 1)}>Increment</button>
    </div>
  );
}

export default Counter;
```

## Rendu et composants React

- **Définition** : dans React, le rendu est le processus par lequel les composants apparaissent dans l’interface utilisateur (UI), en général le navigateur. Le processus de rendu comporte trois étapes : trigger, render et commit.

L’étape trigger se produit quand React détecte qu’un changement a eu lieu et que l’interface utilisateur (UI) pourrait devoir être mise à jour. Ce changement vient souvent d’une mise à jour du state ou des props.

Une fois le trigger déclenché, React entre dans l’étape render. Ici, React réévalue tes composants et détermine quoi afficher. Pour cela, React utilise une copie légère du « vrai » DOM appelée virtual DOM. Avec le virtual DOM, React peut rapidement vérifier ce qui doit changer dans le composant.

L’étape commit est celle où React prend les changements préparés depuis le virtual DOM et les applique au vrai DOM. Autrement dit, c’est l’étape où tu vois le résultat final à l’écran.

## Mettre à jour des objets et des tableaux dans le state

- **Mettre à jour des objets dans le state** : si tu dois mettre à jour un objet dans le state, tu dois d’abord créer un nouvel objet ou copier un objet existant, puis définir le state pour ce nouvel objet. Tout objet placé dans le state doit être considéré en lecture seule. Voici un exemple qui définit le nom, l’âge et la ville d’un utilisateur. La fonction `handleChange` gère les mises à jour des informations de l’utilisateur :

```jsx
import { useState } from "react";

function Profile() {
  const [user, setUser] = useState({ name: "John Doe", age: 31, city: "LA" });

  const handleChange = (e) => {
    const { name, value } = e.target;

    setUser((prevUser) => ({...prevUser, [name]: value}));
  };

  return (
    <div>
      <h1>User Profile</h1>
      <p>Name: {user.name}</p>
      <p>Age: {user.age}</p>
      <p>City: {user.city}</p>

      <h2>Update User Age </h2>
      <input type="number" name="age" value={user.age} onChange={handleChange} />

      <h2>Update User Name </h2>
      <input type="text" name="name" value={user.name} onChange={handleChange} />

      <h2>Update User City </h2>
      <input type="text" name="city" value={user.city} onChange={handleChange} />
    </div>
  );
}

export default Profile;
```

- **Mettre à jour des tableaux dans le state** : quand tu mets à jour des tableaux dans le state, il est important de ne pas modifier directement le tableau avec des méthodes comme `push()` ou `pop()`. À la place, tu dois créer un nouveau tableau lors de la mise à jour du state :

```jsx
const addItem = () => {
  const newItem = {
    id: items.length + 1,
    name: `Item ${items.length + 1}`,
  };

  // Creates a new array
  setItems((prevItems) => [...prevItems, newItem]);
};
```

Si tu veux retirer des éléments d’un tableau, tu dois utiliser la méthode `filter()`, qui renvoie un nouveau tableau après avoir filtré ce que tu veux retirer :

```jsx
const removeItem = (id) => {
  setItems((prevItems) => prevItems.filter((item) => item.id !== id));
};
```

## Référencer des valeurs avec les refs

- **Attribut `ref`** : tu peux accéder à un nœud DOM dans React avec l’attribut `ref`. Voici un exemple qui montre une `ref` pour donner le focus à un élément `input`. La propriété `current` sert à accéder à la valeur actuelle de cette `ref` :

```jsx
import { useRef } from "react";

const Focus = () => {
  const inputRef = useRef(null);

  const handleFocus = () => {
    if (inputRef.current) {
      inputRef.current.focus();
    }
  };

  return (
    <div>
      <input ref={inputRef} type="text" placeholder="Enter text" />
      <button onClick={handleFocus}>Focus Input</button>
    </div>
  );
};

export default Focus;
```

## Travailler avec le hook `useEffect`

- **Hook `useEffect()`** : dans React, un effet est tout ce qui se produit en dehors du processus de rendu du composant. Autrement dit, tout ce que React ne gère pas directement dans le rendu de l’UI. Exemples courants : récupérer des données, mettre à jour le titre de l’onglet du navigateur, lire ou écrire dans le local storage, obtenir la localisation de l’utilisateur, et bien plus. Ces opérations interagissent avec le monde extérieur et s’appellent des effets de bord (side effects). React fournit le hook `useEffect` pour les gérer. `useEffect` te permet d’exécuter une fonction après le rendu ou la mise à jour du composant.

```js
import { useEffect } from "react";

useEffect(() => {
 // Your side effect logic (usually a function) goes here
}, [dependencies]);
```

La fonction d’effet s’exécute après le rendu du composant, tandis que l’argument optionnel `dependencies` contrôle quand l’effet s’exécute.

Note que `dependencies` peut être un tableau de « valeurs réactives » (state, props, fonctions, variables, etc.), un tableau vide, ou être omis entièrement. Voici comment ces options contrôlent le fonctionnement de `useEffect` :

- Si `dependencies` est un tableau qui inclut une ou plusieurs valeurs réactives, l’effet s’exécutera chaque fois qu’elles changent.

- Si `dependencies` est un tableau vide, `useEffect` ne s’exécute qu’une fois, au premier rendu du composant.

- Si tu omets `dependencies`, l’effet s’exécute à chaque rendu ou mise à jour du composant.

## Comment créer des hooks personnalisés

- **Hooks personnalisés** : un hook personnalisé te permet d’extraire une logique réutilisable des composants, comme la récupération de données, la gestion du state, le basculement, et des effets de bord comme le suivi du statut en ligne. Dans React, tous les hooks intégrés commencent par le mot `use`, donc ton hook personnalisé devrait suivre la même convention.

Voici un exemple de création d’un hook `useDebounce` :

```jsx
function useDebounce(value, delay) {
  const [debouncedValue, setDebouncedValue] = useState(value);

  useEffect(() => {
    const handler = setTimeout(() => {
      setDebouncedValue(value);
    }, delay);

    return () => {
      clearTimeout(handler);
    };
  }, [value, delay]);

  return debouncedValue;
}

export { useDebounce };
```

## Travailler avec les formulaires dans React

- **Inputs contrôlés** : c’est quand tu stockes la valeur du champ dans le state et que tu la mets à jour via des événements `onChange`. Cela te donne un contrôle total sur les données du formulaire et permet une validation instantanée et un rendu conditionnel.

```jsx
import { useState } from "react";

function App() {
  const [name, setName] = useState("");

  const handleChange = (e) => {
    setName(e.target.value);
  };

  const handleSubmit = (e) => {
    e.preventDefault();
    console.log(name);
  };

  return (
    <>
      <form onSubmit={handleSubmit}>
        <label htmlFor="name">Your name</label> <br />
        <input value={name} id="name" onChange={handleChange} type="text" />
        <button type="submit">Submit</button>
      </form>
    </>
  );
}

export default App;
```

- **Inputs non contrôlés** : au lieu de gérer les inputs via le hook `useState`, les inputs non contrôlés en HTML conservent leur propre state interne grâce au DOM. Comme le DOM contrôle les valeurs des inputs, tu dois récupérer les valeurs des champs avec une `ref`.

```jsx
import { useRef } from "react";

function App() {
 const nameRef = useRef();

 const handleSubmit = (e) => {
   e.preventDefault();
   console.log(nameRef.current.value);
 };

 return (
   <form onSubmit={handleSubmit}>
     <label htmlFor="name">Your</label>{" "}
     <input type="text" ref={nameRef} id="name" />
     <button type="submit">Submit</button>
   </form>
 );
}

export default App;
```

## Travailler avec le hook `useActionState`

- **Server Actions** : ce sont des fonctions qui s’exécutent sur le serveur pour permettre la gestion de formulaires directement côté serveur, sans endpoints d’API. Voici un exemple issu d’une application Next.js :

```js
"use server";

async function submitForm(formData) {
 const name = formData.get("name");
 return { message: `Hello, ${name}!` };
}
```

La directive `"use server"` marque la fonction comme une server action.

- **Hook `useActionState`** : ce hook met à jour le state selon le résultat d’une soumission de formulaire. Voici la syntaxe de base du hook `useActionState` :

```js
const [state, action, isPending] = useActionState(actionFunction, initialState, permalink);
```

- `state` est le state actuel renvoyé par l’action.
- `action` est la fonction qui déclenche la server action.
- `isPending` est un booléen qui indique si l’action est en cours d’exécution.
- Le paramètre `actionFunction` est la server action elle-même.
- `initialState` représente le point de départ du state avant l’exécution de l’action.
- `permalink` est une chaîne optionnelle qui contient l’URL unique de la page que le formulaire modifie.

## Récupération de données dans React

- **Options pour récupérer des données** : il existe de nombreuses façons de récupérer des données dans React. Tu peux utiliser l’API Fetch native, ou des outils tiers comme Axios ou SWR.
- **Variables d’état couramment utilisées lors de la récupération de données** : quelle que soit la méthode choisie pour récupérer tes données dans React, tu auras besoin de suivre certaines pièces de state. La première est les données elles-mêmes. La deuxième indique si les données sont encore en cours de récupération. La troisième capture les erreurs éventuelles pendant le processus.

```js
const [data, setData] = useState(null);
const [loading, setLoading] = useState(true);
const [error, setError] = useState(null);
```

Comme la récupération de données est un effet de bord, il vaut mieux utiliser l’API `Fetch` à l’intérieur d’un hook `useEffect`.

```js
useEffect(() => {
  const fetchData = async () => {
    try {
      const res = await fetch("https://jsonplaceholder.typicode.com/posts");

      if (!res.ok) {
        throw new Error("Network response was not ok");
      }

      const data = await res.json();
      setData(data);
    } catch (err) {
      setError(err);
    } finally {
      setLoading(false);
    }
  };

  fetchData();
}, []);
```

Ensuite, tu peux afficher un message de chargement si la récupération n’est pas terminée, un message d’erreur s’il y a eu une erreur, ou les résultats.

```jsx
if (loading) {
  return <p>Loading...</p>;
}

if (error) {
  return <p>{error.message}</p>;
}

return (
  <ul>
    {data.map((post) => (
      <li key={post.id}>{post.title}</li>
    ))}
  </ul>
);
```

Si tu veux utiliser Axios, tu dois l’installer et l’importer :

```bash
npm i axios
```

```js
import axios from "axios";
```

Ensuite, tu peux récupérer les données avec `axios.get` :

```js
const [data, setData] = useState(null);
const [loading, setLoading] = useState(true);
const [error, setError] = useState(null);

useEffect(() => {
  const fetchData = async () => {
    try {
      const res = await axios.get(
        "https://jsonplaceholder.typicode.com/users"
      );
      setData(res.data);
    } catch (err) {
      setError(err);
    } finally {
      setLoading(false);
    }
  };

}, []);
```

## Travailler avec le hook `useOptimistic`

- **Hook `useOptimistic`** : ce hook sert à garder l’UI réactive pendant qu’une action asynchrone se termine en arrière-plan. Il aide à gérer les « mises à jour optimistes » dans l’UI : une stratégie où tu fournis des mises à jour immédiates selon le résultat attendu d’une action, comme l’attente d’une réponse serveur.

Voici la syntaxe de base :

```js
const [optimisticState, addOptimistic] = useOptimistic(actualState, updateFunction);
```

- `optimisticState` est le state temporaire qui se met à jour tout de suite pour une meilleure expérience utilisateur.
- `addOptimistic` est la fonction qui applique la mise à jour optimiste avant que le state réel change.
- `actualState` est la vraie valeur de state issue du résultat d’une action, comme la récupération de données depuis un serveur.
- `updateFunction` est la fonction qui détermine comment le state optimiste doit se mettre à jour quand elle est appelée.

Voici un exemple d’utilisation du hook `useOptimistic` dans un composant `TaskList` :

```js
"use client";

import { useOptimistic } from "react";

export default function TaskList({ tasks, addTask }) {
  const [optimisticTasks, addOptimisticTask] = useOptimistic(
    tasks,
    (state, newTask) => [...state, { text: newTask, pending: true }]
  );

  async function handleSubmit(e) {
    e.preventDefault();
    const formData = new FormData(e.target);

    addOptimisticTask(formData.get("task"));

    addTask(formData);
    e.target.reset();
  }

  return <>{/* UI */}</>;
}
```

- **`startTransition`** : sert à rendre une partie de l’UI et à marquer une mise à jour de state comme une transition non urgente. Cela permet à l’UI de rester réactive pendant des mises à jour coûteuses. Voici la syntaxe de base :

```js
startTransition(action)
```

L’`action` effectue une mise à jour de state ou déclenche une logique liée à la transition. Cela garantit que les mises à jour urgentes de l’UI (comme la saisie ou les clics) ne sont pas bloquées.

## Travailler avec le hook `useMemo`

- **Hook `useMemo`** : ce hook sert à mémoïser des valeurs calculées. Voici un exemple de mémoïsation du résultat du tri d’un grand tableau. La `expensiveSortFunction` ne s’exécutera que quand `largeArray` change :

```js
);
```

## React Router

- **Introduction** : React Router est une bibliothèque tierce qui te permet d’ajouter le routage à tes applications React. Pour commencer, tu dois installer React Router dans un projet React existant comme ceci :

```bash
npm i react-router
```

Ensuite, dans le fichier `main.jsx` ou `index.jsx`, tu dois configurer la structure des routes comme ceci :

```jsx
import { StrictMode } from "react";
import { createRoot } from "react-dom/client";
import { BrowserRouter, Routes, Route } from "react-router";
import App from "./App.jsx";

import "./index.css";

createRoot(document.getElementById("root")).render(
  <StrictMode>
    <BrowserRouter>
      <Routes>
        <Route path="/" element={<App />} />
      </Routes>
    </BrowserRouter>
  </StrictMode>
);
```

Les props `path` et `element` associent l’URL et les composants d’UI. Ici, on configure une route pour la page d’accueil qui pointe vers le composant `App`.

- **Vues multiples et configuration des routes** : dans les applications plus grandes, il est courant d’avoir plusieurs vues et routes configurées comme ceci :

```jsx
<Routes>
  <Route index element={<Home />} />
  <Route path="about" element={<About />} />

  <Route path="products">
    <Route index element={<ProductsHome />} />
    <Route path=":category" element={<Category />} />
    <Route path=":category/:productId" element={<ProductDetail />} />
    <Route path="trending" element={<Trending />} />
  </Route>
</Routes>
```

La prop `index` dans ces exemples représente la route par défaut pour un segment de chemin donné. Donc le composant `Home` s’affichera au chemin racine `/` tandis que `ProductsHome` s’affichera au chemin `/products`.

- **Imbriquer des routes** : tu peux imbriquer des routes dans d’autres routes : le chemin de la route enfant est alors ajouté à celui de la route parente.

```jsx
<Route path="products">
  <Route path="trending" element={<Trending />} />
</Route>
```

Dans l’exemple ci-dessus, le chemin des produits tendance sera products/trending.

- **Segments dynamiques** : un segment dynamique est une partie du chemin d’URL qui est dynamique.

```jsx
<Route path=":category" element={<Category />} />
```

Dans cet exemple, on a un segment dynamique appelé `category`. Quand un utilisateur navigue vers une URL comme products/brass-instruments, la vue passe au composant `Category` et tu peux récupérer dynamiquement les données appropriées selon le segment.

- **Hook `useParams`** : ce hook sert à accéder aux paramètres dynamiques d’un chemin d’URL.

```js
import { useParams } from "react-router";

export default function Category() {
  let params = useParams();
   {/* Accessing the category param: params.category */}
   {/* rest of code goes here */}
}
```

## Gestion du state

- **Context API** : le contexte désigne le cas où un composant parent met des informations à disposition des composants enfants sans les passer explicitement via des props. `createContext` sert à créer un objet de contexte que d’autres composants liront. Le `Provider` fournit les valeurs de contexte aux composants enfants.

```js
import { useState, createContext } from "react";

const CounterContext = createContext();

const CounterProvider = ({ children }) => {
  const [count, setCount] = useState(0);

  return (
    <CounterContext.Provider value={{ count, setCount }}>
      {children}
    </CounterContext.Provider>
  );
};

export { CounterContext, CounterProvider };
```

- **Redux** : Redux gère le state en fournissant un store central et un contrôle strict des mises à jour. Il utilise un motif prévisible avec actions, reducers et middleware. Les actions sont des payloads d’information qui envoient des données de ton application au store Redux, souvent déclenchées par des interactions utilisateur. Les reducers sont des fonctions qui précisent comment le state doit changer en réponse à ces actions, en garantissant une mise à jour immuable. Le middleware, lui, fait le pont entre le dispatch d’actions et le reducer, pour étendre les fonctionnalités de Redux (logs, opérations async, etc.) sans modifier le flux central.

- **Zustand** : cette solution de gestion du state convient bien aux applications de petite à moyenne taille. Elle utilise un hook `useStore` pour accéder au state directement dans les composants et les pages. Tu peux ainsi modifier et accéder aux données sans actions, reducers ni provider.

## Différences entre performance réelle et perçue

- **Performance perçue** : c’est la façon dont les utilisateurs perçoivent la performance d’un site. Ils l’évaluent en termes de réactivité et de fiabilité. C’est une mesure subjective, donc difficile à quantifier, mais très importante : l’expérience utilisateur détermine le succès ou l’échec d’un site.
- **Performance réelle** : c’est la performance objective et mesurable du site. On la mesure avec des métriques comme le temps de chargement de page, le temps de réponse serveur et le temps de rendu. Ces mesures dépendent de facteurs liés au réseau et au code lui-même.

## Techniques pour améliorer la performance perçue

- **Lazy Loading** : cette technique réduit autant que possible le temps de chargement initial en chargeant les ressources non essentielles en arrière-plan.
- **Minimiser les délais de polices** : si ton site a des polices personnalisées, essaie aussi de minimiser les délais de chargement des polices, sinon tu risques un scintillement ou l’affichage de la police de repli pendant le chargement. Une suggestion : utiliser une police de repli proche de la police personnalisée pour que le changement soit plus subtil.
- **Indicateurs de chargement** : afficher un indicateur pour un processus long dès que l’utilisateur clique sur un élément peut l’aider à se sentir connecté au processus, et raccourcir la sensation d’attente.

## Concepts fondamentaux de performance

- **Ordre source** : cela désigne la façon dont les éléments HTML sont structurés dans le document. Cela détermine ce qui se charge en premier et peut fortement impacter la performance et l’accessibilité.

Quelques bonnes pratiques pour l’ordre source :

- Placer le contenu critique comme les titres, la navigation ou le texte principal plus haut dans la structure HTML.
- Différer les scripts non essentiels (analytics, widgets tiers) pour qu’ils ne bloquent pas le rendu.
- Utiliser l’amélioration progressive pour garantir que l’expérience de base fonctionne même avant le chargement des styles et scripts. L’amélioration progressive consiste à construire des sites en faisant d’abord fonctionner la page avec HTML.

Voici un exemple de bon ordre source, avec les bonnes pratiques qu’on vient de voir :

```html
<h1>Welcome to FastSite!</h1>
<p>Critical information loads first.</p>
<script src="slow-script.js" defer></script>
```

- **Critical Rendering Path** : séquence d’étapes que suit le navigateur pour convertir le code en pixels à l’écran.
- **Latence** : temps qu’il faut à une requête pour voyager entre le navigateur et le serveur. Autrement dit, une latence élevée égale des pages lentes.

Quelques façons de réduire la latence :

- Utiliser des CDN (Content Delivery Networks) pour servir les fichiers depuis des emplacements plus proches.
- Activer la compression (Gzip, etc.) pour réduire la taille des fichiers.
- Optimiser les images et utiliser le lazy loading.

```html
<img src="placeholder.jpg" data-src="real-image.jpg" loading="lazy">
```

## Améliorer l’INP

- **Définition** : l’INP (Interaction to Next Paint) évalue la réactivité globale d’une page en mesurant le temps entre une interaction utilisateur (clic, touche) et le moment suivant où le navigateur met à jour l’affichage. Un INP plus bas indique une page plus réactive.

Voici quelques façons d’améliorer l’INP :

- Réduire le travail du thread principal en découpant les longues tâches JavaScript.
- Utiliser `requestIdleCallback()` pour les scripts non critiques. Cela met en file une fonction à appeler pendant les périodes d’inactivité du navigateur.
- Différer ou charger à la demande les assets lourds (vu plus tôt).
- Optimiser les gestionnaires d’événements. S’ils s’exécutent trop souvent ou font des opérations lourdes, ils peuvent ralentir la page et augmenter l’INP. La solution : le debouncing. Le debouncing garantit que la fonction ne s’exécute qu’après que l’utilisateur a arrêté de taper pendant un court délai — par exemple 300 ms. Cela évite des calculs inutiles et améliore la performance.

## Comment le rendu fonctionne dans le navigateur

- **Comment fonctionne le rendu** : d’abord le navigateur parse le HTML et construit le DOM. Ensuite, il traite le CSS et construit le CSS Object Model, ou CSSOM. C’est une autre structure en arbre qui dicte comment les éléments doivent être stylés. Enfin, le navigateur peint les pixels à l’écran, en rendant chaque élément selon les styles et la mise en page calculés. Sur des pages complexes, cela peut impliquer plusieurs couches compositées pour former le rendu final.

## Comment la performance impacte la durabilité

- **Contexte** : Internet représente environ 2 % des émissions mondiales de carbone — autant que l’industrie aérienne ! Chaque octet transféré demande de l’électricité, des centres de données aux appareils utilisateurs. Des fichiers plus gros et des scripts inefficaces signifient plus de consommation d’énergie. Un site performant n’est pas seulement plus rapide : il réduit aussi le traitement et la consommation d’énergie inutiles.

## Façons de réduire les temps de chargement de page

- **Optimiser les assets média** : les grandes images et vidéos sont souvent responsables de chargements lents. En les optimisant, tu peux nettement accélérer ton site : compression d’images, formats modernes comme WebP, lazy loading, etc.
- **Tirer parti du cache navigateur** : le cache permet aux navigateurs de stocker localement des parties de ton site, ce qui réduit les temps de chargement pour les visiteurs qui reviennent.
- **Minifier et compresser les fichiers** : réduire la taille de tes fichiers accélère les téléchargements. Cela inclut la réduction des fichiers transmis et la minification des fichiers CSS et JavaScript.

## Améliorer le « time to usable »

- **Définition** : le « time to usable » est l’intervalle entre le moment où un utilisateur demande une page et celui où il peut interagir utilement avec elle. Pour l’améliorer, tu peux charger tes assets en lazy loading ou minimiser les ressources qui bloquent le rendu.

## Métriques clés pour mesurer la performance

- **First Contentful Paint ou FCP** : mesure la rapidité d’apparition du premier contenu — texte ou image — à l’écran. Un bon FCP est en dessous de 1,8 seconde, un mauvais au-dessus de 3 secondes. Tu peux vérifier ton FCP avec Chrome DevTools, onglet Performance.
- **Total Blocking Time** : montre combien de temps le thread principal est bloqué par de lourdes tâches JavaScript. Si le Total Blocking Time (TBT) est élevé, les utilisateurs ressentent des interactions lentes. Pour améliorer le TBT, découpe les longues tâches et diffère les scripts non essentiels.
- **Bounce Rate** : pourcentage de visiteurs qui partent sans interagir. Un fort taux de rebond peut venir d’une page trop lente.
- **Unique Users** : cette métrique suit combien de visiteurs individuels viennent sur ton site. Pour voir le Bounce Rate et les Unique Users, tu peux utiliser Google Analytics, qui te permet de suivre ces métriques et d’améliorer l’engagement.

## Outils courants de mesure de la performance

- **Chrome DevTools** : outil intégré à Google Chrome pour analyser et déboguer la performance en temps réel. DevTools montre les temps de chargement, l’usage CPU et les délais de rendu. Il est particulièrement utile pour mesurer le First Contentful Paint (FCP), c’est-à-dire la vitesse à laquelle un utilisateur voit le premier contenu visible. Si ton site paraît lent, DevTools t’aidera à repérer les goulots d’étranglement.
- **Lighthouse** : outil automatisé qui vérifie performance, SEO et accessibilité.
- **WebPageTest** : te permet de tester le chargement de ton site depuis différents lieux et appareils. Il donne une décomposition détaillée du Speed Index, du Total Blocking Time et d’autres métriques clés. Si tu veux savoir comment de vrais utilisateurs vivent ton site dans le monde, c’est l’outil adapté.
- **PageSpeed Insights** : analyse ton site et propose des améliorations rapides pour mobile et desktop. Il indique ce qui ralentit ton site et donne des recommandations précises (optimiser les images, retirer les scripts qui bloquent le rendu, réduire les temps de réponse serveur). C’est un moyen rapide de voir comment Google perçoit la performance de ton site.
- **Real User Monitoring** : les outils RUM suivent le comportement réel des utilisateurs. Parmi les plus connus : Google Analytics (temps de chargement, bounce rates) et New Relic ou Datadog (problèmes de performance en temps réel). Pour des données d’utilisateurs réels, les outils RUM sont essentiels.

## Travailler avec les Web APIs de performance

- **Définition** : les Web APIs de performance permettent aux développeurs de suivre directement dans le code l’efficacité du chargement et de la réponse d’une page. Elles permettent de mesurer les temps de chargement, les délais de rendu et d’interaction, et le temps d’exécution JavaScript.
- **`performance.now()`** : cette API fournit des horodatages haute précision (en millisecondes) pour mesurer combien de temps différentes parties de ton site mettent à charger.

```js
const start = performance.now();
// Run some code here
const end = performance.now();

console.log(`Execution time: ${end - start}ms`);
```

- **Performance Timing API** : cette API te donne une décomposition de chaque étape du chargement de page, de la résolution DNS jusqu’à `DOMContentLoaded`.

```js
const timing = performance.timing;

const pageLoadTime = timing.loadEventEnd - timing.navigationStart;
console.log(`Page load time: ${pageLoadTime}ms`);
```

- **`PerformanceObserver`** : cette API écoute des événements de performance comme les layout shifts, les longues tâches et les interactions utilisateur.

```js
const observer = new PerformanceObserver((list) => {
  list.getEntries().forEach((entry) => {
    console.log(`Long task detected: ${entry.duration}ms`);
  });
});

observer.observe({ type: "longtask", buffered: true });
```

## Techniques pour améliorer la performance CSS

- **Animations CSS** : animer certaines propriétés CSS (dimensions, position, mise en page) déclenche un processus appelé « reflow », où le navigateur recalcule la position et la géométrie de certains éléments. Cela entraîne un repaint, coûteux en calcul. Il est donc recommandé de réduire le nombre d’animations CSS autant que possible, ou au moins de laisser à l’utilisateur la possibilité de les activer ou les désactiver.

## Techniques pour améliorer la performance JavaScript

- **Code Splitting** : découper ton code JavaScript en modules pour tâches critiques et non critiques est aussi utile. Tu pourras ainsi précharger les modules critiques au plus tôt et différer les non critiques pour rendre la page aussi vite que possible.
- **Manipulation du DOM** : rappelle-toi que la manipulation du DOM désigne le processus de modification dynamique du contenu d’une page avec JavaScript via le Document Object Model (DOM). Manipuler le DOM est coûteux en calcul. Réduire la quantité de manipulations DOM dans ton code JavaScript améliorera la performance.

## Tests manuels et automatisés

- **Tests manuels** : en test manuel, un testeur parcourt manuellement chaque partie de l’application et teste différentes fonctionnalités pour vérifier qu’elles fonctionnent correctement. Si des bugs apparaissent, le testeur les signale à l’équipe logicielle pour qu’ils soient corrigés.
- **Tests automatisés** : en test automatisé, tu automatises tes tests en écrivant un programme séparé qui vérifie si ton application se comporte comme prévu.

## Tests unitaires

- **Tests unitaires** : en test unitaire, tu testes chaque fonction pour t’assurer que tout fonctionne comme prévu. Les tests unitaires peuvent aussi servir de documentation, car ils représentent le comportement attendu de ton code.
- **Principe de responsabilité unique** : ce principe recommande de garder chaque fonction petite et responsable d’une seule chose.
- **Frameworks de test JavaScript courants** : Jest, Mocha et Vitest. Jest est un framework populaire pour les tests unitaires.

Voici un exemple de tests unitaires avec Jest.

D’abord, tu peux créer une fonction responsable de renvoyer une chaîne nouvellement formatée :

```javascript
export function getFormattedWord(str) {
  if (!str) return '';
  return str.charAt(0).toUpperCase() + str.slice(1);
}
```

Dans un fichier séparé `getFormattedWord.test.js`, tu peux écrire des tests pour vérifier que la fonction fonctionne comme prévu. Le fichier `getFormattedWord.test.js` ressemblera à ceci :

```javascript
import { getFormattedWord } from "./getFormattedWord.js";
import { test, expect } from "jest";

test('capitalizes the first letter of a word', () => {
  expect(getFormattedWord('hello')).toBe('Hello');
});
```

- **Fonction `expect`** : la fonction `expect` sert à tester une valeur.
- **Matcher** : un matcher est une fonction qui vérifie si la valeur se comporte comme prévu. Dans l’exemple ci-dessus, le matcher est `toBe()`. Jest propose une variété de matchers.

Pour utiliser Jest, tu dois d’abord installer le package `jest` avec `npm i jest`. Tu devras aussi ajouter un script à ton fichier `package.json` comme ceci :

```js
"scripts": {
  "test": "jest"
},
```

Ensuite, tu peux exécuter la commande `npm run test` pour lancer tes tests.

## Cycle de vie du développement logiciel

- **Différentes étapes du cycle de vie du développement logiciel** :
  - **Étape de planification** : l’équipe de développement recueille les exigences du travail proposé auprès des parties prenantes.
  - **Étape de conception** : l’équipe logicielle découpe les exigences et choisit les meilleures approches de solution.
  - **Étape d’implémentation** : l’équipe découpe les exigences en tâches gérables et les implémente.
  - **Étape de test** : tests manuels et automatisés du nouveau travail. Parfois, l’équipe teste l’application tout au long du développement pour attraper et corriger les problèmes.
  - **Étape de déploiement** : l’équipe déploie les nouveaux changements dans un environnement de build ou de test.
  - **Étape de maintenance** : correction des problèmes signalés par les clients dans l’application de production.

- **Différents modèles du cycle de vie du développement logiciel** :
  - **Modèle Waterfall** : chaque phase du cycle doit être terminée avant que la suivante puisse commencer.
  - **Modèle Agile** : se concentre sur le développement itératif en découpant le travail en sprints.

## BDD et TDD

- **TDD** : le développement piloté par les tests (Test-driven development) met l’accent sur l’écriture des tests en premier. Écrire les tests avant de construire les fonctionnalités donne un retour en temps réel aux développeurs pendant le développement.
- **BDD** : le développement piloté par le comportement (Behavior-driven development) aligne une série de tests sur les objectifs métier. Les scénarios de test BDD devraient être écrits dans un langage compréhensible par les profils techniques et non techniques. Un exemple de syntaxe est Gherkin.
- **Frameworks de test BDD** : Cucumber, JBehave et SpecFlow, par exemple.

## Assertions dans les tests unitaires

- **Assertion** : les assertions servent à vérifier que le code se comporte comme prévu.
- **Bibliothèques d’assertions** : Chai est une bibliothèque d’assertions courante. D’autres bibliothèques JavaScript courantes sont `should.js` et `expect.js`.

Voici un exemple d’assertion avec Chai qui vérifie que la valeur renvoyée par la fonction `addThreeAndFour` est égale au nombre 7 :

```js
assert.equal(addThreeAndFour(), 7);
```

- **Bonnes pratiques** : quelle que soit la bibliothèque d’assertions, tu devrais écrire des messages d’assert et d’échec clairs pour comprendre quels tests échouent et pourquoi.

## Mocking, faking et stubbing

- **Mocking** : remplacer de vraies données par de fausses données qui simulent le comportement de vrais composants. Par exemple, tu peux mocker la réponse d’API en test au lieu de faire des appels API continus.
- **Stubbing** : les stubs sont des objets qui renvoient des réponses prédéfinies ou des données factices pour un comportement attendu. Par exemple, tu peux stubber le comportement d’une connexion base de données dans tes tests sans dépendre d’une vraie connexion.
- **Faking** : les fakes sont des versions simplifiées de vrais composants, sans la complexité ni les effets de bord. Par exemple, tu peux faker une base de données en stockant les données en mémoire au lieu d’interagir avec la vraie base. Cela te permet de mimer des opérations en mémoire, beaucoup plus rapides.

## Tests fonctionnels

- **Tests fonctionnels** : vérifient si les fonctionnalités de l’application fonctionnent comme prévu. L’objectif est de tester le système dans son ensemble face à plusieurs scénarios.
- **Tests non fonctionnels** : se concentrent sur des aspects comme la performance et la fiabilité.
- **Smoke testing** : vérification préliminaire du système pour repérer des problèmes basiques ou critiques avant des tests plus poussés.

## Tests de bout en bout

- **Tests de bout en bout** : les tests end-to-end, ou E2E, testent des scénarios réels du point de vue de l’utilisateur. Ils aident à garantir que ton application se comporte correctement et de façon prévisible. Cependant, leur mise en place, leur conception et leur maintenance prennent du temps.
- **Frameworks de tests de bout en bout** : Playwright est un framework E2E populaire développé par Microsoft. D’autres outils : Cypress, Selenium et Puppeteer.

```js
  execSync("node ./tools/scripts/seed/seed-demo-user --set-true isDonating");

...

test("The menu should have a supporters link", async ({ page }) => {
```

## Tests d’utilisabilité

- **Tests d’utilisabilité** : de vrais utilisateurs interagissent avec l’application pour découvrir d’éventuels problèmes de design, d’expérience utilisateur ou de fonctionnalités. Ces tests se concentrent sur le caractère intuitif de l’application.
- **Quatre types courants de tests d’utilisabilité** :
  - **Exploratoire** : les utilisateurs interagissent avec les différentes fonctionnalités pour mieux comprendre comment elles fonctionnent.
  - **Comparatif** : tu compares l’expérience utilisateur de ton application à des applications similaires sur le marché.
  - **Évaluation** : tu étudies à quel point l’application est intuitive à utiliser.
  - **Validation** : tu identifies les problèmes majeurs qui empêcheraient l’utilisateur d’utiliser efficacement l’application.
- **Outils de tests d’utilisabilité** : Loop11, Maze, Userbrain, UserTesting et UXTweak, par exemple.

## Tests de compatibilité

- **Tests de compatibilité** : l’objectif est de s’assurer que ton application fonctionne dans différents environnements informatiques.
- **Différents types de tests de compatibilité** :
  - **Compatibilité ascendante (backwards)** : le logiciel est compatible avec les versions antérieures.
  - **Compatibilité descendante (forwards)** : le logiciel et les systèmes fonctionneront avec les versions futures.
  - **Compatibilité matérielle** : capacité du logiciel à fonctionner correctement dans différentes configurations matérielles.
  - **Compatibilité des systèmes d’exploitation** : capacité à fonctionner sur différents OS, comme macOS, Windows, et des distributions Linux comme Ubuntu et Fedora.
  - **Compatibilité réseau** : le logiciel peut fonctionner dans différentes conditions réseau (vitesses, protocoles, réglages de sécurité, etc.).
  - **Compatibilité navigateurs** : l’application web fonctionne de façon cohérente sur différents navigateurs (Google Chrome, Safari, Firefox, etc.).
  - **Compatibilité mobile** : il est important de s’assurer que tes applications fonctionnent sur une variété d’appareils Android et iOS, téléphones et tablettes compris.

## Tests de performance

- **Tests de performance** : tu testes la vitesse, la réactivité, la scalabilité et la stabilité d’une application sous différentes charges. L’objectif est de résoudre tout goulot d’étranglement de performance.
- **Différents types de tests de performance** :
  - **Load testing** : détermine le comportement du système en charge normale et en pic.
  - **Stress testing** : tu testes l’application sous des charges extrêmes pour voir comment le système réagit.
  - **Soak testing (endurance)** : type de load testing où tu testes le système avec une charge élevée pendant une période prolongée.
  - **Spike testing** : tu augmentes et diminues dramatiquement les charges et analyses les réactions du système.
  - **Breakpoint testing (capacity)** : tu incrémentes lentement la charge jusqu’au point où le système commence à échouer ou se dégrader.

## Tests de sécurité

- **Tests de sécurité** : aident à identifier vulnérabilités et faiblesses.
- **Principes de sécurité** :
  - **Confidentialité** : protège contre la divulgation d’informations sensibles à des destinataires non prévus.
  - **Intégrité** : empêche des utilisateurs malveillants de modifier les informations utilisateur.
  - **Authentification** : vérifie l’identité de l’utilisateur pour s’assurer qu’il est autorisé à utiliser le système.
  - **Autorisation** : détermine quelles actions les utilisateurs authentifiés peuvent effectuer ou quelles parties du système ils peuvent accéder.
  - **Disponibilité** : garantit que les informations et services sont disponibles pour les utilisateurs autorisés quand ils en ont besoin.
  - **Non-répudiation** : garantit que l’émetteur et le destinataire ont une preuve de livraison et une vérification de l’identité de l’émetteur. Protège contre le déni d’avoir envoyé l’information.
- **Menaces de sécurité courantes** :
  - **Cross-Site Scripting (XSS)** : injections de scripts malveillants dans une page web, exécutés dans le contexte du navigateur de la victime.
  - **SQL Injection** : permet à des utilisateurs malveillants d’injecter du code malveillant dans une base de données.
  - **Attaque Denial-of-Service (DoS)** : des utilisateurs malveillants inondent un site de requêtes ou de trafic, ce qui ralentit voire fait planter le serveur et rend le site indisponible.
- **Catégories d’outils de tests de sécurité** :
  - **Static Application Security Testing** : évaluent le code source pour identifier des vulnérabilités.
  - **Dynamic Application Security Testing** : interagissent avec le front-end de l’application pour découvrir des faiblesses potentielles. Les outils DAST n’ont pas accès au code source.
- **Tests de pénétration (pentest)** : type de test de sécurité qui simule des cyberattaques sur l’application pour identifier des vulnérabilités.

## Tests A/B

- **Tests A/B** : comparent deux versions d’une page ou d’une application pour étudier laquelle performe mieux. On parle aussi de bucket testing ou split testing. Les tests A/B te permettent de prendre des décisions plus data-driven et d’améliorer continuellement l’expérience utilisateur.
- **Outils pour les tests A/B** : GrowthBook et LaunchDarkly, par exemple.

## Tests alpha et bêta

Une fois le développement initial et les tests logiciels terminés, il est important de faire tester l’application par des testeurs et de vrais utilisateurs. C’est là qu’interviennent les tests alpha et bêta.

- **Tests alpha** : réalisés par un groupe sélectionné de testeurs qui parcourent l’application pour s’assurer qu’il n’y a pas de bugs avant la mise sur le marché. Les tests alpha font partie des tests d’acceptation et utilisent des techniques white box et black box.
- **Tests bêta** : l’application est mise à disposition de vrais utilisateurs. Ils peuvent interagir et fournir des retours. Les tests bêta sont aussi une forme de test d’acceptation utilisateur.
- **Tests d’acceptation** : garantissent que l’application répond aux exigences métier et aux besoins des utilisateurs avant sa sortie.
- **Black box testing** : se concentre uniquement sur le comportement attendu de l’application.
- **White box testing** : le testeur connaît les composants internes et effectue des tests dessus.

## Tests de régression

- **Régression** : situations où de nouveaux changements cassent involontairement des fonctionnalités existantes.
- **Tests de régression** : aident à attraper les problèmes de régression. Tu relances des tests fonctionnels sur des parties de ton application pour t’assurer que tout fonctionne encore comme prévu.
- **Outils pour les tests de régression** : Puppeteer, Playwright, Selenium et Cypress.
- **Techniques de tests de régression** :
  - **Unit regression testing** : liste d’éléments à tester à chaque fois que des changements majeurs ou des correctifs sont implémentés.
  - **Partial regression testing** : approches ciblées pour s’assurer que les nouveaux changements n’ont pas cassé des aspects précis de l’application.
  - **Complete regression testing** : lance des tests sur toutes les fonctionnalités du codebase. C’est l’option la plus longue et la plus détaillée.
- **Retesting** : sert à vérifier des problèmes connus et s’assurer qu’ils ont été résolus. En revanche, les tests de régression cherchent des problèmes inconnus qui pourraient être apparus suite à de récents changements.

## Qu’est-ce que TypeScript

- **JavaScript** : JavaScript est un langage à typage dynamique. Cela signifie que les variables peuvent recevoir n’importe quelles valeurs à l’exécution. Le défi d’un langage à typage dynamique est que le manque de sûreté de type peut introduire des erreurs.

Par exemple, même si ta fonction JavaScript attend un tableau, tu peux quand même l’appeler avec un nombre :

```javascript
const getRandomValue = (array) => {
  return array[Math.floor(Math.random() * array.length)];
}

console.log(getRandomValue(10));
```

La sortie `console` pour l’exemple ci-dessus sera `undefined`.

- **TypeScript** : TypeScript étend le langage JavaScript pour inclure le typage statique, ce qui aide à attraper les erreurs dues à des décalages de types avant d’exécuter ton code.

Par exemple, tu peux définir un type pour le paramètre `array` comme suit :

```typescript
const getRandomValue = (array: string[]) => {
  return array[Math.floor(Math.random() * array.length)];
}
```

Cette définition de type indique à TypeScript que le paramètre `array` doit être un tableau de chaînes. Ensuite, quand tu appelles `getRandomValue` en passant un nombre, tu obtiens une erreur appelée erreur de compilation.

- **Compilateur** : tu dois d’abord compiler le code TypeScript en JavaScript classique. Quand tu lances le compilateur, TypeScript évalue ton code et lève une erreur pour tout problème où les types ne correspondent pas.

## Types de données en TypeScript

- **Types de données primitifs en TypeScript** : pour les types primitifs `string`, `null`, `undefined`, `number`, `boolean` et `bigint`, TypeScript offre des mots-clés de type correspondants.

```typescript
let str: string = "Naomi";
let num: number = 42;
let bool: boolean = true;
let nope: null = null;
let nada: undefined = undefined;
```

- **Tableau** : tu peux définir un tableau d’un type précis avec deux syntaxes différentes.

```typescript
const arrOne: string[] = ["Naomi"];
const arrTwo: Array<string> = ["Camperchan"];
```

- **Objets** : tu peux définir la structure exacte d’un objet.

```typescript
const obj: { a: string, b: number } = { a: "Naomi", b: 42 };
```

Si tu veux un objet avec des clés quelconques, mais où toutes les valeurs doivent être des chaînes, il y a deux façons de le définir :

```typescript
const objOne: Record<string, string> = {};
const objTwo: { [key: string]: string } = {};
```

- **Autres types utiles en TypeScript** :
  - **`any`** : `any` indique qu’une valeur peut avoir n’importe quel type. Cela dit au compilateur d’arrêter de se soucier du type de cette variable.
  - **`unknown`** : `unknown` dit à TypeScript que tu te soucies du type de la valeur, mais que tu ne le connais pas encore. `unknown` est généralement préféré à `any`.
  - **`void`** : type spécial que tu utiliseras surtout en définissant des fonctions. Les fonctions sans valeur de retour utilisent un type de retour `void`.
  - **`never`** : représente un type qui n’existera jamais.

- **Mot-clé `type`** : ce mot-clé ressemble à `const`, mais au lieu de déclarer une variable, tu déclares un type.

Il est utile pour déclarer des types personnalisés comme des union types ou des types qui n’incluent que des valeurs précises :

```typescript
type stringOrNumber = string | number;
type bot = "camperchan" | "camperbot" | "naomi";
```

- **`interface`** : les interfaces ressemblent à des classes pour les types. Elles peuvent implémenter ou étendre d’autres interfaces, sont spécifiquement des types d’objets, et sont généralement préférées sauf si tu as besoin d’une fonctionnalité propre à une déclaration `type`.

```typescript
interface wowie {
  zowie: boolean;
  method: () => void;
}
```

- **Définir le type de retour** : tu peux aussi définir le type de retour de la fonction.

L’exemple ci-dessous définit la valeur de retour comme une chaîne. Si tu essaies de renvoyer autre chose, TypeScript donnera une erreur de compilation.

```typescript
const getRandomValue = (array: string[]): string => {
  return array[Math.floor(Math.random() * array.length)];
}
```

## Génériques

- **Définir un type générique** : tu peux définir un type générique et y faire référence dans ta fonction. On peut le voir comme un paramètre spécial fourni à une fonction pour contrôler le comportement de sa définition de type.

Voici un exemple de définition d’un type générique pour une fonction :

```typescript
const getRandomValue = <T>(array: T[]): T => {
  return array[Math.floor(Math.random() * array.length)];
}
const val = getRandomValue([1, 2, 4])
```

La syntaxe `<T>` indique à TypeScript que tu définis un type générique `T` pour la fonction. `T` est un nom courant pour les types génériques, mais tu peux en utiliser un autre.

Ensuite, tu indiques à TypeScript que le paramètre `array` est un tableau de valeurs correspondant au type générique, et que la valeur renvoyée est un seul élément de ce même type.

- **Spécifier un argument de type dans un appel de fonction** : tu peux passer un argument de type à un appel de fonction avec des chevrons entre le nom de la fonction et ses paramètres.

Voici un exemple de passage d’un argument de type à un appel de fonction :

```typescript
const email = document.querySelector<HTMLInputElement>("#email");
console.log(email.value);
```

Cela indique à TypeScript que l’élément que tu t’attends à trouver sera un élément input.

## Rétrécissement de types (type narrowing)

- **Rétrécissement par truthiness** : dans l’exemple ci-dessous, tu obtiens une erreur de compilation en essayant d’accéder à la propriété `value` de `email` parce que `email` pourrait être `null`.

```typescript
const email = document.querySelector<HTMLInputElement>("#email");
console.log(email.value);
```

Tu peux utiliser une instruction conditionnelle pour confirmer que `email` est truthy avant d’accéder à la propriété :

```typescript
const email = document.querySelector<HTMLInputElement>("#email");
if (email) {
  console.log(email.value);
}
```

Les vérifications de truthiness peuvent aussi fonctionner dans l’autre sens :

```typescript
const email = document.querySelector<HTMLInputElement>("#email");
if (!email) {
  throw new ReferenceError("Could not find email element!")
}
console.log(email.value);
```

Lever une erreur met fin à l’exécution logique de ce code, ce qui signifie qu’au moment d’atteindre l’appel `console.log()`, TypeScript sait que `email` ne peut pas être `null`.

- **Optional chaining** : le chaînage optionnel `?.` est aussi une forme de type narrowing, selon le même principe : l’accès à la propriété ne peut pas se produire si la valeur `email` est `null`.

```typescript
const email = document.querySelector<HTMLInputElement>("#email");
console.log(email?.value);
```

- **Opérateur `typeof`** : tu peux utiliser une condition pour vérifier le type de la variable avec l’opérateur `typeof`.

```typescript
const myVal = Math.random() > 0.5 ? 222 : "222";
if (typeof myVal === "number") {
  console.log(myVal / 10);
}
```

- **Mot-clé `instanceof`** : si l’objet vient d’une classe, tu peux utiliser le mot-clé `instanceof` pour rétrécir le type.

```typescript
const email = document.querySelector("#email");

if (email instanceof HTMLInputElement) {
    console.log(email.value);
}
```

- **Casting** : quand TypeScript ne peut pas déterminer automatiquement le type d’une valeur, comme le résultat de la méthode `request.json()` dans l’exemple ci-dessous, tu obtiens une erreur de compilation. Une façon de résoudre cela est de caster le type, mais cela affaiblit la capacité de TypeScript à attraper des erreurs potentielles.

```typescript
interface User {
    name: string;
    age: number;
}

const printAge = (user: User) =>
  console.log(`${user.name} is ${user.age} years old!`)

const request = await fetch("url")
const myUser = await request.json() as User;
printAge(myUser);
```

- **Type Guard** : au lieu de caster le type, tu peux écrire un type guard :

```typescript
interface User {
    name: string;
    age: number;
}

const isValidUser = (user: unknown): user is User => {
  return !!user &&
    typeof user === "object" &&
    "name" in user &&
    "age" in user;
}
```

La syntaxe `user is User` indique que ta fonction renvoie une valeur booléenne qui, quand elle est vraie, signifie que la valeur `user` satisfait l’interface `User`.

## Fichier `tsconfig`

- **`tsconfig.json`** : les réglages du compilateur TypeScript vivent dans un fichier `tsconfig.json` à la racine de ton projet.

```json
{
  "compilerOptions": {
    "rootDir": "./src",
    "outDir": "./prod",
    "lib": ["ES2023"],
    "target": "ES2023",
    "module": "ES2022",
    "moduleResolution": "Node",
    "esModuleInterop": true,
    "skipLibCheck": true,
    "strict": true
  },
  "exclude": ["test/"]
}
```

Voici les descriptions des options du compilateur utilisées dans l’exemple ci-dessus :

- **`compilerOptions`** : la propriété `compilerOptions` contrôle le comportement du compilateur TypeScript.
- **`rootDir` et `outDir`** : `rootDir` et `outDir` indiquent à TypeScript quel répertoire contient tes fichiers source, et lequel doit contenir le JavaScript transpilé.
- **`lib`** : la propriété `lib` détermine quelles définitions de types le compilateur utilise, et te permet d’inclure le support de versions ES précises, du DOM, etc.
- **`module` et `moduleResolution`** : `module` et `moduleResolution` travaillent ensemble pour gérer la façon dont ton package utilise les modules — CommonJS ou ECMAScript.
- **`esModuleInterop`** : `esModuleInterop` facilite l’interopérabilité entre CommonJS et les modules ES en créant automatiquement des objets namespace pour les imports.
- **`skipLibCheck`** : l’option `skipLibCheck` saute la validation des fichiers `.d.ts` non référencés par des imports dans ton code.
- **`strict`** : le flag `strict` active plusieurs vérifications, comme une bonne gestion des types nullables et un avertissement quand TypeScript retombe sur `any`.
- **`exclude`** : la propriété de premier niveau `exclude` dit au compilateur d’ignorer ces fichiers TypeScript pendant la compilation.
